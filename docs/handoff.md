# Slidecast Extender — Handoff (fresh-chat starter)

**Date:** 2026-09-20. **Repo:** `~/Projects/ffxiv-tools/SlidecastExtender/` (in `ffxiv-tools` monorepo).

## TL;DR

Build the **wire-side** half of FFXIV slidecasting first: during a cast, suppress outgoing `Move`
packets at the plaintext boundary (server keeps believing you're standing still, its cast timer
completes, `ActionEffect`/`CastFinish` arrive), then flush the real position on resolve. The
**local** half (the client cancels its own cast bar the instant you move — *before* any
`CastInterrupt` — so the bar dies locally; surviving that is the hard 50%) is deferred to M1 and
is the real difficulty.

**What exists (2026-09-20, third session — on the game machine):** the wire side is complete,
tested (58 green), and **installed to `~/.xlcore/devPlugins/SlidecastExtender/`** (visible in
game through the prefix link). Hook targets resolve **at runtime via FFXIVClientStructs** — the
Ghidra step is gone. The packet table uses the **real 7.56h opcodes**, and the engine follows
the **real zone protocol** (ActionRequest → ActorCast → Effect/ActorControl), not the first
draft's imagined one. Remaining work: enable the plugin in game, run Observe
(`docs/re/capture-checklist.md`), confirm the VERIFY layout constants from the hex dumps, then
Live.

## Third-session changes (the real-protocol rework)

Ground-truthed against the local install (game `2026.09.15.0000.0000`, Dalamud 15.0.3.5,
FFXIVClientStructs shipped with it):

- **Hook targets:** `ZoneClient.SendPacket` (send; opcode at packet+0) and
  `PacketDispatcher.OnReceivePacket` (receive; opcode at packet+2, IPC payload at +0x10) — the
  exact functions Dalamud's NetworkMonitorWidget hooks, resolved via
  `ZoneClient.MemberFunctionPointers.SendPacket` /
  `PacketDispatcher.StaticVirtualTablePointer->OnReceivePacket`. No hardcoded addresses;
  FFXIVClientStructs carries the per-patch signatures. `HookTargets.cs` is now a `TryResolve`.
- **Opcodes (FFXIVOpcodes Global 7.56h):** send `UpdatePositionHandler`=920, `ActionRequest`=913,
  `ActionRequestGroundTargeted`=891; receive `ActorCast`=354, `Effect`=787, `ActorControl`=607,
  `ActorControlSelf`=516, `UpdatePositionInstance`=411. The first draft's ids (0x0030 Move,
  0x0123 Cast, 0x0131 ActionEffect…) were wrong; there is no client→server "Cast" packet at all.
- **Protocol flow correction:** the window opens on send `ActionRequest` gated by a
  **cast-time provider** (plugin looks up Lumina `Action.Cast100ms` × 100; 0 = instant → no
  window, so melee instants are never suppressed). Receive `ActorCast` refines the deadline with
  the server's authoritative cast time (`ActorCastPacket` layout from FFXIVClientStructs:
  actionId @ payload+4, castTime f32 seconds @ payload+8). Receive `Effect` resolves. Interrupt
  is an `ActorControl(Self)` **category**, not an opcode — `-1`/disabled until Observe finds it
  (`InterruptActorControlCategory`). Frozen position = the last Move the engine let through
  (what the server believes), not a field in the cast packet.
- **Boundary realities:** neither hook passes a packet length — the engine copies bounded
  per-id prefixes (`WirePackets.*CaptureBytes`); the flush template is a 64-byte Move capture.
  Send-hook drop = return `true` without calling the original (pretend success; **VERIFY** the
  caller doesn't retry). Flush reuses the last Move's captured `this`/`a3`/`a4`/`a5`.
- **Move layout is float32 x/y/z** at VERIFY offsets 16/20/24 in the send packet (structural
  guess; Observe hex dumps confirm — every detail line includes the raw hex for exactly this).
- **Engine API:** `StartCast(actionId, durationMs, tsMs)`, new `RefineCast(actionId,
  castTimeSec, tsMs)`, `SetCastTimeProvider(Func<uint,long>)`, `OnClientToSend(IntPtr, long)`
  (no size/flags — the real boundary has neither).
- **LogSink** writes next to the plugin DLL (`SpecialFolder.ApplicationData` would land inside
  the Wine prefix on this box).
- **Plugin manifest** is generated by DalamudPackager from csproj properties (done in session
  two); the plugin builds on this Linux box with
  `dotnet build SlidecastExtender.Plugin.slnx -p:EnableWindowsTargeting=true -p:OutputPath="$HOME/.xlcore/devPlugins/SlidecastExtender/"`.
- Dalamud config confirms dev plugins are enabled (`DoPluginTest`, `DevMode`) and
  `~/.xlcore/devPlugins` is the same folder as the in-game
  `C:\Users\you\AppData\Roaming\XIVLauncher\devPlugins` (shared link).

## Original handoff (the source document)

> FFXIV Slidecast Extender — Handoff
>
> ### TL;DR
> Build a plugin that extends the FFXIV "slidecast" window by faking stillness to the server so
> the cast isn't interrupted mid-move. The wire-side logic is buildable now; the local-side
> blocker (surviving the client's own cast interrupt) is a hard reverse-engineering problem and
> is the real difficulty.
>
> ### 1. What we're building
> An FFXIV plugin that, on a long cast, lets the character move (slide) without losing the cast,
> by:
> - Locally: still animating/moving the character so it looks normal.
> - On the wire: NOT reporting the new position to the server (or replaying the cast-start
>   position) until the cast resolves, so the server thinks you're standing still → doesn't
>   interrupt → sends ActionEffect / CastFinish on timer.
> - After resolve: flush your real position. Server correction / collision snaps you (and others)
>   to the legal resolved position.
> This extends the small window stock slidecast exploits (server finishes early while local
> animation lags).
>
> ### 2. The key insight (why it's hard — read before coding)
> The original desync idea has a load-bearing flaw:
> - The interrupt is local, not server-side.
> - The client cancels the local cast bar the instant the character moves — before any
>   CastInterrupt arrives from the server. The server's CastInterrupt is a sync/confirmation,
>   not the cause of the bar dying.
> So a pure wire-side "fake stillness" fixes the server's belief, not the client's bar.
> Result: character slides, no cast bar (a normal interrupted cast), not slidecasting.
> Therefore: to keep the bar up while sliding, the local cast object must survive local movement.
> That decoupling lives in the client's native game logic, not the network layer. That's the
> hard 50%.
> The wire side (your desync) is the easier 50% and worth building first to validate the concept.
>
> ### 3. Architecture: two halves
> **Wire side (buildable / testable first):**
> - In-process hook of the client's network send/receive — at the plaintext boundary (before
>   encryption / after decryption). No crypto cracking needed.
> - Intercept Cast, Move, CastInterrupt, ActionEffect/CastFinish packets.
> - On cast start: snapshot the cast-start position.
> - During the cast: suppress Move packets (or replay frozen position).
> - On finish: flush corrected Move to the real position.
>
> Risks on the wire side:
> - Server snap: flush = large position jump in one packet; server corrects it, may snap you/others
>   away from your visual position.
> - Max velocity / distance clamps: server may reject or clamp the flush → worse than a clean snap.
> - Collision: resolved against reported (frozen) pos, not visual. Flush into wall/other player
>   gets corrected.
> - Finish re-validation: server may cross-check finish vs cast-start delta and re-interrupt /
>   drop ActionEffect.
>
> **Local side (the real blocker):**
> - Hook the client's cast-object lifecycle so it doesn't cancel on movement during the cast window.
> - Reverse-engineer: find the function owning local cast / "is-casting" state and the interrupt
>   trigger; gate it.
> - Breaks on every client update; deep native work.
> - Cheap lane to try first: Realscript (client's managed event bridge) to maybe defer the local
>   interrupt before going deep native.
>
> ### 4. Tooling decision
> - SDK = Dalamud (FFXIV/Dalamud/Dalamud on GitHub). The community-native SDK.
> - Managed (C#) plugin API.
> - Native C++ runtime → lets a managed plugin do inline/patch hooks into arbitrary client
>   functions (this is how we get to the plaintext send/receive without writing our own
>   injector).
> - Realscript event bridge.
> - Loader (DLL injection).
>
> Caveat: Dalamud gives you how to hook a function, not which function. The local
> cast-interrupt target isn't a documented symbol (closed-source client) → needs RE (Ghidra/IDA)
> against the live binary.
>
> Verification (dev aid only): Wireshark/tshark — traffic shape sanity. Not load-bearing.
> Wine: user is on a Fedora box. FFXIV runs under Wine/Proton for play, but loading a native DLL
> + observing plaintext in-process under Wine is unproven/fragile. Don't bet the prototype on it.
> "Client plays under Wine" ≠ "we can inject + watch packets."
>
> ### 5. Environment
> - User is on Fedora Linux. (Wine is the path to run the client, with the caveats above.)
> - The working AI agent is a Pyodide/WASM (browser) sandbox: no OS, no subprocess, no package
>   installs.
>   - ✅ Can author C# / C++ / Realscript / Python code.
>   - ✅ Can design hook points + protocol logic.
>   - ❌ Cannot compile, load the DLL, or observe the live client from here.
> So: agent writes the code + architecture; the user (or a Ghidra/tshark MCP) confirms symbols
> and runs it on the machine.
>
> ### 6. Status / where we are
> No code written yet. Concept validated in principle; difficulty correctly identified (local side
> is the hard blocker, not the wire side). Plan: build the wire-side prototype first (Dalamud
> plugin: send/receive hooks + Cast snapshot + Move suppression + finish flush). Slot the exact
> hook function names as placeholders to confirm against the live binary.
>
> ### 7. Suggested next steps
> 1. Scaffold the Dalamud plugin (C# + native hooks): send/receive hook registration; Cast handler
>    → snapshot position; Move handler → suppress during cast; ActionEffect/finish handler → flush
>    position.
> 2. Identify the hook targets (Ghidra/IDA or live inspection): the network packet
>    send/receive / serialize functions to inline-hook; the local cast-object + interrupt function
>    (the deep one).
> 3. Test the wire side on the client (Windows, or Fedora+Wine) and observe plaintext before/after.
> 4. Only then tackle the local-side interrupt.
>
> ### 8. Key terms / packet names
> - **Cast** — cast-start packet.
> - **Move** — position-update packet.
> - **CastInterrupt** — server tells client the cast was interrupted.
> - **ActionEffect / CastFinish** — the cast completed successfully.
> - **Plaintext boundary** = in-process send/receive, before encryption / after decryption.
>
> ### 9. Open questions to confirm on the machine
> 1. Does the client inject + the plugin load reliably under Wine on Fedora? (vs. Windows)
> 2. What are the exact function signatures for the network send/receive hooks?
> 3. Can Realscript defer the local cast interrupt, or is a native hook required?
> 4. How does the server react to a large single-packet position flush — clamp, reject, or clean
>    snap?
> 5. Does the client's Move suppression cause any client-side prediction drift (e.g., movement
>    animation vs. position) that's visible before the flush?
>

## Design contract (don't break these without thinking)

- **Two halves, one rule:** core knows nothing about Dalamud; plugin is a thin adapter (hooks +
  log + timer). Any new logic goes in core.
- **Modes:** `Off` (hooks pass through, zero work) / `Observe` (log the wire, change nothing —
  the *first in-game run*) / `Live` (suppression + flush).
- **Suppression:** `Drop` (default: Move packets simply not sent during the window; server keeps
  the frozen position) vs `ReplayFrozen` (packet sent with x/y/z overwritten to the cast-start
  position, via `WirePackets.PatchMovePosition` **in place on the client's buffer** just before the
  original send — the client rebuilds the packet from its own state next Move, so the wire-only
  patch is self-consistent).
- **Flush:** `Immediate` (default: one Move packet with the final real position on resolve —
  accepts the server-snap risk, documented) vs `Staged` (N interpolated steps, per-step distance
  capped at `StagedMaxStepUnits`, one step per `StagedStepIntervalMs`, remaining steps emitted in
  one burst at `StagedFlushTimeoutMs` — fail-open).
- **Fail-open (ADR-002) on every exit path:** `ActionEffect`/`CastFinish` → flush + normal;
  `CastInterrupt`/`Interrupt` → flush + normal; timeout (`duration + GracePeriodMs`) → flush +
  normal; flush-sink failure → abandon staged flush + normal. Never let the engine get stuck
  in a window.
- **Zero-drift fast path:** if last real position ≈ frozen position (0.01 u), log and skip the
  flush entirely (no snap into your own position).
- **Threading:** hooks run on the client network thread; a 250 ms timer also calls the tracker.
  `WireExtender` serializes tracker access with a lock; the lock is held short (no external calls
  inside except `sink.Send`, which just calls the original send on the same thread).
- **Flush delivery:** the engine builds the flush packet from a *captured real Move packet* (the
  last suppressed Move, as `byte[]` template) with x/y/z patched — byte-compatible with what the
  client would send. `IFlushSink.Send` is what the plugin forwards to the *original* Send function
  (captured `this`/flags).
- **Clock:** `Environment.TickCount` (ms, process-relative); the tracker only does deltas +
  `durationMs` from the Cast packet, so no wall-clock dependency.

**Symptom:** on Pictomancer under PL5 autorotation (crowded Cosmic Exploration FATE), casts kept
dying mid-cast — including standing still. The 09-21 city test (empty area) had passed.

**Root cause (from `wire-20260925-105217.log`):** `ActorControl` is broadcast for **every actor
in range**, like `ActorCast`. The engine treated any category-15 packet as OUR cast's interrupt.
In a busy FATE, other players' cast interrupts closed our window mid-cast, which (a) flushed our
real position mid-cast when moving — the server then REALLY cancelled the cast — and (b) released
PL5's IPC hold early. Proof in the log: stationary casts "interrupted" with zero suppressed moves
and nothing flushed (34653 @ 1.15 s of 2.26 s; motif 34666 @ 0.185 s of 3 s), plus
`cast-interrupt: no active window; ignored` orphans — category-15 packets with no cast of ours
active at all.

**Fix:** the receive hook's `targetId` (the actor the packet is about) is now threaded through
(`PacketSink` → `WireExtender.OnClientReceived(data, targetId, ts)`); the plugin wires
`SetLocalEntityIdProvider(() => IPlayerState.EntityId)` (API 15: `LocalPlayer` moved to
`IObjectTable`; `IPlayerState.EntityId` is the direct source). `ActorCast` refine and
`ActorControl` interrupts are honored only when `targetId` matches the local player;
`ActorControlSelf` is honored unconditionally (self by definition). No provider = legacy
trust-everything (tests); provider reporting 0 (loading screen) = trust nothing — the deadline
backstop still closes the window (ADR-002). Observe-mode ActorCast/ActorControl lines now log
`targetId` for verification. 73 green (4 new correlation tests).
